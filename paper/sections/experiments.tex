\section{Experiments}\label{sec:experiments}

\subsection{Setup}\label{sec:setup}
\paragraph{Data.} \emph{LongMemEval-S} \cite{wu2025longmemeval} has 500 questions, each with its own store of about 490 turns. \emph{LoCoMo} \cite{maharana2024locomo} has 10 long conversations. \emph{BEAM} \cite{tavakoli2026beam} has long conversations of about 2,000 turns, of which 35 from the 1M set serve for development and \V{n-beam} questions in 55 conversations from the 100K and 500K sets for evaluation. \emph{RepoMem}, which we introduce here, turns real repositories into memory streams, at 14 snapshots over six years. Each interval is a session in which a simulated agent records commit notes and facts observed in changed files. Facts (constants, signatures, symbol locations, dependency constraints) come from static analysis, so a fact is stale exactly when the same key held another value at an earlier snapshot. Fact queries ask for the current value, and task queries use a real later commit subject, with earlier commits on the same files as gold. RepoMem runs with slot keys, as a host agent would supply them, and without.

\paragraph{Test protocol.} A held-out test is a set of repositories that no fit, threshold or design choice has touched. We froze the method, ran the test once with a single script, and treated the set as spent afterwards: it can then serve for development, or as a check on a later change, but never again as a test. Models were later refitted on spent repositories, and each new test used new ones, so every test below scores repositories its model had not seen. Benchmarks have no verdicts, so learning plays no part in them. Unless noted, recall and gate results measure release 0.5.0, file notes 0.5.2 and the chains 0.6.1. Later releases changed the read path only through the near-twin rule, file notes and learning, and Section~\ref{sec:stale} gives the effect of the rule on the main test. Appendix~\ref{app:past} lists the earlier tests.

\paragraph{Baselines.} Recency, BM25 (FTS5), dense retrieval (all-MiniLM-L6-v2 \cite{hf_minilm}), hybrid RRF \cite{cormack2009rrf}, hybrid followed by a cross-encoder (ms-marco-MiniLM-L-6-v2) on the top 50, MMR \cite{carbonell1998mmr}, Generative Agents scoring \cite{park2023generative} with constant importance, facility location under a knapsack as in PACMS \cite{pacms2026}, hybrid with superseded versions removed, in the spirit of \cite{rasmussen2025zep}, and hybrid keeping only the newest of near-twins. All methods share candidate generators, token counts (\texttt{cl100k\_base}) and a 14-token per-item overhead, and every ranking is filled greedily to the budget, which already makes the baselines budget-aware. Systems that need an LLM on write were not run.

\paragraph{Statistics.} The independent unit is a conversation on BEAM and a repository on RepoMem, since queries within a conversation are dependent and seeds repeat RepoMem queries. We give bootstrap intervals over units and $p$-values from two-sided sign-flip permutation tests on unit means, with Holm correction across budgets within a comparison. With $n$ units the smallest possible two-sided $p$ is $2^{1-n}$, so tests on six repositories cannot pass correction across budgets, and there we read the interval and the count of units on each side. An interval that contains zero on few units is weak evidence that two methods are equal.

\subsection{Development findings}\label{sec:dev}
Three findings from development data shaped the design, on a fit that came before the current one. The relevance model is close to calibrated: over ten equal-count bins the expected calibration error is \V{ece-lme} on LongMemEval-S, \V{ece-locomo} on LoCoMo, \V{ece-repomem} on RepoMem and \V{ece-beam-dev} on BEAM-1M, against base rates near one percent, though the highest-scored one percent of BEAM-1M candidates are predicted at \V{top-beam-dev-predicted} and observed at \V{top-beam-dev-observed}. The knapsack solver hardly matters: mean recall is \V{rule-beam-dev-density} for density greedy against \V{rule-beam-dev-dp} for an exact knapsack on BEAM-1M. Cost does matter on BEAM-1M, where ranking by probability alone falls to \V{rule-beam-dev-rank}, but not on RepoMem, at \V{rule-repomem-rank} against \V{rule-repomem-density}. The candidate pool matters where a question has many evidence turns: on BEAM-1M the top 100 from each retriever reach \V{pool-beam-dev-pool100} of the evidence, and adding the neighbours of the 50 best hits reaches \V{pool-beam-dev-nb50x1}.

\subsection{Stale facts}\label{sec:stale}
Table~\ref{tab:finalstale} covers queries whose fact changed, at 1024 tokens, on the main test. With keys, every method that follows version chains injects no stale version. Without keys, hybrid and the reranker inject one \V{fstp-repomem-final-plain-hybrid-stale_any}\% of the time and \kanerva \V{fstp-repomem-final-plain-kanerva-stale_any}\%. The plain rule of keeping the newest near-twin reaches \V{fstp-repomem-final-plain-hybrid-dedup-stale_any}\%, so the gain comes from that rule and not from a probabilistic model of validity. The error, a stale version listed above or instead of the current one, stays near zero at \V{fst-repomem-final-plain-kanerva-stale_error} against \V{fst-repomem-final-plain-hybrid-stale_error} for hybrid.

The current twin rule also applies to the main test's repositories, which we checked after the fact. Recall moves by \V{tr-third-dense} with vectors and stale injection falls from \V{tr-third-stale-kanerva-0.5}\% to \V{tr-third-stale-kanerva}\%, while on BEAM nothing moves. In lexical stores recall moves by \V{tr-third-lex} and stale injection rises from \V{tr-third-stale-kanerva-lex-0.5}\% to \V{tr-third-stale-kanerva-lex}\%. Most of the small loss in strict fact recall is the labelling effect above.

The labels on the main test have two known flaws. Of the \V{flaw-changed} changed facts, \V{flaw-moved} (\V{flaw-moved-p}\%) only moved to another file and kept their value, so injecting the older note does no harm, and \V{flaw-bogus} dependency queries read console-script entries as version constraints. Without these queries, stale injection at release 0.5.0 is \V{flaw-stale-kanerva-clean}\% for \kanerva and \V{flaw-stale-kanerva-lex-clean}\% lexically, and the lead over hybrid stays at \V{flaw-lead-clean}. We kept the dataset as it was, so that the tests stay comparable.

The class hazard adds nothing we can measure. Removing it on the main test moves recall by \V{hz-vectors} (interval \V{hz-vectors-ci}) and leaves stale injection at \V{hz-stale-with}\%, so the fall in stale injection comes from version chains and the near-twin rule.

The rule depends on near-identical text. On the \emph{natural-language} updates of LongMemEval, evidence for a fact and for its update are not near-twins, so the rule does not fire, and on development data \kanerva injects the outdated turn on \V{up-kanerva-inject} of questions against \V{up-hybrid-inject} for hybrid, since it finds more evidence of both kinds. Listing items newest first keeps the error to \V{up-kanerva-error} against \V{up-hybrid-error} for hybrid in rank order. Recognising that a free-text statement replaces an older one takes semantics the store does not have, and that is the job of the write path (Section~\ref{sec:writepath}).

\subsection{The write path without keys}\label{sec:writepath}
A note without a key replaces an older one only if someone says so, so \texttt{memory\_remember} lists similar notes and the host agent decides. We first replay streams with no keys and ask for this list as each note is written, with no LLM involved (Table~\ref{tab:writepath}). On the main test with vectors the older version of a changed fact comes first on \V{wp-vectors-repomem-final-top1} of changed notes and is on the list on \V{wp-vectors-repomem-final-top3}, while natural language is much harder, at \V{wp-vectors-lme-updates-top1} and \V{wp-vectors-lme-updates-top3} on LongMemEval updates. The list also appears on \V{wp-vectors-repomem-final-shown_on_other_notes-p}\% of notes that replace nothing, so an agent that retired whatever came first would lose good notes, and the value of the list depends on the agent's judgement. An oracle that marks the true older version whenever the list shows it would take stale injection on the main test from \V{wp-vectors-repomem-final-current_rule-stale-p}\% to \V{wp-vectors-repomem-final-oracle_simulated-stale-p}\%, which is what a perfect agent could reach.

To measure a real agent, Claude Code with the plugin and \V{awp-model} gets a store replayed up to a note and an instruction to remember it, and the store afterwards shows what it did. A \emph{verbatim} note keeps a text word for word. An \emph{own} note is what an agent normally writes: a first session turns the older conversation turn into a short note in its own words, and a second, fresh session does the same with the newer turn. Earlier rounds shaped the hint, the server's instructions and the list, and the sample below is the one they had not seen.

Over \V{awp-trials} trials the agent fixed \V{awp-lme-own-notes-changed-fixed} of \V{awp-lme-own-notes-changed-n} changed facts in its own conversation notes, \V{awp-lme-updates-changed-fixed} of \V{awp-lme-updates-changed-n} in word-for-word turns and \V{awp-repomem-final-changed-fixed} of \V{awp-repomem-final-changed-n} on code facts, and it left the store alone in \V{awp-other-clean} of \V{awp-other-n} trials on notes that replace nothing. In three of the four conversation misses the agent gave a defensible reason, such as a list of dated entries that stay true. In \V{awp-extra} trials it changed a note the labels did not mark, and we read them all: most were right or harmless, and one was a real loss, a signature note retired along with a moved function.

\subsection{Learning from verdicts}\label{sec:verdicts}
\paragraph{Implicit signals.} A natural signal counts a note as used when its identifiers appear in later tool calls. In the transcripts of Section~\ref{sec:gate} the sessions never had these notes, so every firing of this signal is wrong, and it fires on \V{rs-vectors-fired}\% of the notes a prompt brought and on \V{rs-vectors-random}\% of random notes from the same store. Good labels alone do not help the benchmarks either. With feedback simulated from evidence labels (Table~\ref{tab:online}), a linear bandit over shared features loses to the fitted model, at \V{on-locomo-online} against \V{on-locomo-static} on LoCoMo and \V{on-repomem-online} against \V{on-repomem-static} on RepoMem, and the system does not use one. The pooled lift gains little, at \V{on-locomo-lift} on LoCoMo and \V{on-repomem-lift} on RepoMem. Those benchmarks rarely repeat a question, whereas in the same transcripts \V{rs-recurrence}\% of turns that touch files return to a file from an earlier session.

\paragraph{Can an agent tell what helped?} Self-reports are known to inflate rewards, so we tested them. Claude Code with \V{awp-model} ran \V{sig-trials} sessions on \V{sig-repos} repositories that no earlier test had read. Each session is a small documentation chore that needs two facts, in a store of true notes about that repository, and in some sessions one fact is held only in an older version while the code shows the current one. A shown note is labelled by how the trial was built, as needed, stale or other, and the agent gives its verdict at the stop, as in normal use. Before the first run we required a verdict in at least four of five sessions, at least four in five marks right, at least three in five needed notes marked, at most one in ten other notes marked, and at least half of stale notes called out. All five bars were met (Table~\ref{tab:signal}). The agent judged \V{sig-coverage}\% of sessions, marked \V{sig-false-hits} of \V{sig-other-n} other notes as helpful, and called \V{sig-stale-misled} of \V{sig-stale-n} stale notes wrong. Those other notes were unrelated facts, which are easy to reject, so these rates are a best case.

\paragraph{Does acting on verdicts help?} Not measurably on the build that ships, and no harm was measured either. Six repositories that nothing had read each carry a store of \V{chain-notes} notes, about the size real projects reach, and a chain of \V{chain-sessions} sessions. Each session asks for one fact, and a need is drawn to repeat an earlier one with probability \V{chain-recurrence}\%, close to the share above. A prompt that names a symbol leaves nothing to learn, since search puts its note first, so a cheap model writes three plain wordings of each need, with no identifier or file name, used in turn. Both arms get the same store and the same chores in the same order, and both give verdicts at each stop. One arm only records, and the other acts as \texttt{KANERVA\_LEARN=auto} does. The second half of each chain is scored. An answer is right if it names the thing asked for, or for a constant holds its value. Settings were chosen on spent repositories. Before the run we required a rise in sessions a note helped or in needed notes shown, or a fall in lookups, with an interval clear of zero, while right answers fell by no more than a twentieth and tokens rose by no more than a quarter.

Table~\ref{tab:chain} gives the results. The limits on the means held and the gain did not appear, so the bar was not met. Right answers were \V{chain-count-right-learned} of \V{chain-scored} against \V{chain-count-right-fixed}, with an interval that reaches past the limit, a note helped in \V{chain-count-helped-learned} sessions in both arms, and lookups were level. The needed note reached the context in \V{chain-needed_shown-learned} of sessions against \V{chain-needed_shown-fixed}, and tokens fell from \V{chain-tokens-fixed} to \V{chain-tokens-learned} per session, both within noise. Lift ran in \V{chain-lift-chains} of the six acting chains and only \V{chain-lift-sessions} scored sessions, and the gate moved by itself in \V{chain-moved}. The agent judged \V{chain-judged-learned} of \V{chain-judged-sessions} sessions in the acting arm and \V{chain-judged-fixed} in the other, so counts of sessions a note helped are a little low in both.

Two earlier runs, on other repositories, led to this design. In the second, on a later build, right answers fell from \V{chainsecond-right-fixed} to \V{chainsecond-right-learned} under a score that wanted a signature's whole parameter list word for word. \paragraph{What the gate hides.} The chains exposed a larger problem than the one lift addresses. Asked plain questions built the same way, with no agent and with probes off, on new stores from those repositories and the others used in this section, the shipped gate and weight floor bring the needed note to the context on \V{pq-default-found} of \V{pq-n} questions, using \V{pq-default-tokens} tokens of a budget of 600, although it is among the candidates on \V{pq-pool}. Moving the gate down by three units gives \V{pq-gate-found} at \V{pq-gate-tokens} tokens, and lowering the floor as well gives \V{pq-wide-found} at \V{pq-wide-tokens}. Probes exist to find this project by project, and the gate has begun to move in the chains, but that happened too rarely and too late in a chain to measure what it brings. Replaying the real prompts of Section~\ref{sec:gate}, with verdicts stood in for by a weak file-overlap label, no project's gate had moved by the end, and probes, which in this replay opened the gate but did not lower the floor, took tokens per prompt from \V{rg-fixed-tokens} to \V{rg-learned-tokens}.

\subsection{Answers from a local model}\label{sec:answers}
Recall says what reaches the context and not what a model does with it, so here a small local model answers each question from the notes a method selected. The memory layer still calls no LLM. The reader is Qwen3-4B in 4-bit form on MLX, pinned by revision, told to answer from the notes alone in as few words as it can, or to say unknown. We take \V{qan-locomo} questions from LoCoMo, \V{qan-lme} from LongMemEval-S, \V{qan-beam-dev} from BEAM-1M and \V{qan-repomem-final} fact queries from the six Python repositories of the main test, without keys, at 256, 512 and 1024 tokens, on release 0.5.0. Only the last set is unseen. Only short extractive answers can be scored without a judge, and an answer counts as right if it has every word of the reference in any order, or for code the whole value as an unbroken run. Scoring rules were fixed on small pilots before the full run. With no notes the score is zero on every set, and the last row of Table~\ref{tab:answers} hands the reader the labelled evidence alone.

Across every comparison and metric, \V{qa-raw} of \V{qa-tests} tests reach raw $p<0.05$ and \V{qa-holm} survive Holm correction, so this test shows no reliable difference between methods. Of the \V{qa-means} means in Table~\ref{tab:answertests}, one reaches raw $p<0.05$: on the main test's facts \kanerva beats BM25 by \V{qad-repomem-final-kanerva_vs_bm25-mean} points (interval \V{qaci-repomem-final-kanerva_vs_bm25-mean}), on all six repositories, which is about what chance gives in that many comparisons. The intervals are wide, so these nulls do not show that methods are equal, but several differences go against \kanerva, and on conversations recall barely converts. At 512 tokens \kanerva leads BM25 in recall by \V{qagap-locomo-recall-512}, \V{qagap-lme-recall-512} and \V{qagap-beam-dev-recall-512} points on LoCoMo, LongMemEval-S and BEAM-1M, and its answers move by \V{qagap-locomo-contain-512}, \V{qagap-lme-contain-512} and \V{qagap-beam-dev-contain-512} points. On the main test's facts the same figures are \V{qagap-repomem-final-recall-512} and \V{qagap-repomem-final-contain-512}. We did not test why.

Stale notes do less harm than retrieval figures suggest (Table~\ref{tab:answerstale}). On \V{qast-n} sampled facts whose value changed, hybrid and BM25 put a stale note in the context nearly every time, yet hybrid's answers give the old value only \V{qast-hybrid-1024-old}\% of the time at 1024 tokens, against \V{qast-kanerva-1024-old}\% for \kanerva. The gate saves tokens rather than mistakes: on \V{qa-foreign} questions no store can answer, \kanerva invents an answer \V{qainvented-kanerva} times without the gate and \V{qainvented-kanerva+gate} times with it, because the reader already refuses.

\subsection{Russian notes}\label{sec:russian}
Russian support adds a Snowball stemmer, stopwords and query patterns, and \texttt{KANERVA\_EMBEDDER=multilingual} adds search across languages. English behaviour is unchanged. We test on XQuAD \cite{artetxe2020xquad}, which gives SQuAD paragraphs and questions in English and in professional Russian translation, with \V{ru-questions} questions over \V{ru-articles} articles. A retrieval counts if it returns the question's paragraph. With a store per article, stemming moves lexical recall from \V{ru-article-ru-ru-stem-off-1024} to \V{ru-article-ru-ru-stem-on-1024} at 1024 tokens (difference \V{rud-article_ru-ru_stem-on_vs_stem-off-1024}, interval \V{ruci-article_ru-ru_stem-on_vs_stem-off-1024}). For a Russian question over English notes, lexical search finds almost nothing, at \V{ru-pooled-ru-en-lexical-1024} in a pooled store, MiniLM fails there too at \V{ru-pooled-ru-en-minilm-1024}, and the multilingual model reaches \V{ru-pooled-ru-en-multilingual-1024}. It gains nothing on English and costs more, \V{ru-size-multilingual} MB against \V{ru-size-minilm} MB on disk, so MiniLM stays the default. This is not coding-agent memory, and the relevance model has not seen Russian.

\paragraph{Latency.} On an M1 Pro, a fresh query at $10^4$ items takes \V{p50-hybrid@10000} ms at the median and \V{p95-hybrid@10000} ms at the 95th percentile, plus \V{encode} ms to embed the query, and lexical retrieval takes \V{p50-lexical@10000} and \V{p95-lexical@10000} ms. \paragraph{Live sessions.} In real Claude Code sessions on small Python and C++ projects with an isolated store, memory carried over: after one session found that the machine has no \texttt{python}, the next went straight to \texttt{python3}, and after a C++ session learned that the tests need a Debug build, the next ran that CMake command first. These are anecdotes and not measurements.
